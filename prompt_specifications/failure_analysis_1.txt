## EXECUTION MODEL — READ BEFORE RESPONDING

The DSL evaluator executes programs as a flat sequence of function calls, one at a time:
- Programs are a semicolon-separated list of terminal function calls: `FUNC1(ARG); FUNC2(ARG); ...`
- Each terminal function receives the current environment state and returns a **flat list of primitive actions**
- The evaluator steps through tokens sequentially: there is NO interpreter support for jumps, branches, or loops at the grammar level

**CONSTRAINT**: Grammar-level control flow constructs (`WHILE ... END`, `IF ... THEN ... ELSE ... END`, `REPEAT N`) are NOT executable by the evaluator. Do NOT suggest them.

Instead, express looping or conditional behavior as **terminal functions** that inspect the environment internally and return the appropriate action sequence.
Each suggested terminal must be independently implementable and MUST NOT call any other terminal function.

### CFG Recommendations
For each recommendation, use one of the formats below:

- ADD terminal: `FUNCTION_NAME LPAR PARAM RPAR` — purpose: <why this function is needed>
- REMOVE terminal: `FUNCTION_NAME` — reason: <why it is not useful or is misleading>
- CHANGE parameter set: `PARAM_NAME` — remove `VALUE_X`, add `VALUE_Y` — reason: <why>
- ADD nonterminal: `NONTERMINAL -> ...` — purpose: <what structural role it adds to the grammar>
- REMOVE nonterminal: `NONTERMINAL` — reason: <why it is unnecessary or harmful>
- ADD production: `NONTERMINAL -> RHS` — purpose: <what programs this enables>
- REMOVE production: `NONTERMINAL -> RHS` — reason: <why this derivation is unhelpful>
- CHANGE production: `NONTERMINAL -> OLD_RHS` to `NONTERMINAL -> NEW_RHS` — reason: <why this better matches the task structure>
- CHANGE start rule: `OLD_START_RULE` to `NEW_START_RULE` — reason: <why the top-level program form should change>
- CHANGE sequencing constraint: <describe how statement ordering, optionality, or allowed program length should change> — reason: <why>

**Constraints for recommendations:**
- Use ONLY UPPERCASE names
- Every suggested terminal function must be implementable as a pure action-sequence generator returning a flat list of primitive actions — it may inspect the environment (a copy is provided) but must NOT require cross-call shared state
- Terminal functions must be independent leaves: do NOT suggest semantics where one terminal calls/invokes/delegates to another terminal 
- Do NOT propose terminals whose meaning depends on executing another terminal by name
- Only reference items, values, or concepts present in the domain (do not invent parameters outside what exists in the domain)
- Do NOT suggest grammar-level loops or conditionals — express those needs as terminal functions instead
- It is valid to recommend changes to terminals, parameter vocabularies, nonterminals, productions, start rules, and sequencing structure, as long as the resulting grammar still produces flat sequences of terminal calls compatible with the evaluator
